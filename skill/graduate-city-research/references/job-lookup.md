# 具体岗位查询与核验

## 适用场景

当用户已经锁定一家公司、一个岗位、一个岗位链接或岗位编号时使用。目标是确认“这是哪一个岗位、现在是否招聘、我能不能投、广告承诺了什么、哪些关键条件仍未确认”，而不是重新统计一个地区的岗位市场。

最低规模的一次查询不需要初始化完整城市项目。若后续要把该岗位纳入城市净结余或批量岗位表，再把标准化结果写入项目的 `data/jobs.csv`，并保留本流程产生的原始证据。

## 输入与歧义处理

优先收集：

```text
公司名称或招聘主体
完整岗位名
工作地点（城市、区县、园区或厂址）
届别、学历和专业
岗位链接、岗位编号、招聘平台
用户可接受的班制、出差、驻场、现场调试和住宿条件
数据截止日
```

只要现有信息足以定位一个唯一岗位，就直接查询。若同名岗位分布在不同地点或属于不同招聘主体，先列出候选及各自岗位编号、地点、学历和来源，再请用户选择；不要把一个地点的薪资或条件套到另一个地点。

如果用户只给出宽泛岗位名，可先返回最多 3 个高质量候选，并说明为何仍需选择。若只有一个候选满足地区、届别和专业条件，可以继续核验，但要标注“由上下文推定”。

## 查询顺序

1. 用户提供链接或编号时，先直接访问该页面，记录 HTTP/页面结果、页面标题、岗位编号、更新时间、采集时间和当前显示内容。
2. 查找该企业的官方招聘官网、校招页面、ATS 或官方公众号对应页面，确认法定招聘主体、岗位编号和工作地点。
3. 在用户授权的招聘平台搜索完整岗位名、岗位编号和地点；核对职位 ID、公司主体、工作地址、职责描述与发布日期。
4. 用公开搜索补充入口，但搜索摘要、缓存页和聚合站只用于发现，不作为薪资、状态或工作条件的最终证据。
5. 同一岗位在多个平台出现时，只生成一条核验卡；把所有 URL 放入来源列表。不同岗位编号、不同厂址或不同签约主体分开处理。

可使用以下检索式辅助定位，但不要将其当作来源：

```text
"<岗位编号>"
site:<企业招聘域名> "<完整岗位名>" "<地点>"
"<企业法定名称>" "<完整岗位名>" "2027" "<地点>"
"<企业名称>" "<岗位名>" "<校招/校园招聘>" "<届别>"
```

## 岗位身份与匹配置信度

为每个候选建立稳定身份，不用岗位标题作为唯一键。

| 匹配置信度 | 判定条件 | 使用边界 |
|---|---|---|
| 高 | 岗位编号/ATS 编号一致，且企业与工作地点一致 | 可作为该岗位的主要记录 |
| 中 | 无岗位编号，但企业原始页的完整标题、地点、职责和招聘主体一致 | 可作为观察，仍需 HR 核验 |
| 低 | 只有相似标题、搜索摘要、转载页或同名岗位 | 只能列为候选，不确认薪资和条件 |

原始求职页是主证据；同一岗位的转载只提供交叉入口。若转载页无法证明与原岗位是同一记录，保留为独立候选并标注“疑似重复”，不得用其增加岗位数或名额。

## 岗位状态

岗位状态必须与岗位条件分开，并记录最后核验时间：

| 状态 | 可接受证据 |
|---|---|
| 原始页明确开放 | 原始页当前可用，页面明确处于招聘中或申请入口有效；记录页面日期 |
| 原始页明确关闭 | 原始页明确显示已结束、已下架、停止招聘或截止日期已过 |
| 状态未确认 | 页面打不开、只有转载、申请按钮状态不明，或信息互相冲突 |
| 仅见搜索摘要/缓存 | 不能据此认定开放；必须继续找原始页 |

即使状态为“开放”，也不意味着岗位会持续开放、HC 仍充足或面试流程仍在进行。用户最终应以招聘方书面回复为准。

## 必须抽取的岗位字段

### 身份与范围

- 企业名称、统一社会信用代码或法定招聘主体（能取得时）
- `requisition_id` / 平台职位 ID 和 `canonical_url`
- 完整岗位名、岗位族、工作地点和实际办公/厂区地址
- 发布日期、最后更新或截止日期、首次和最后一次采集时间
- 岗位状态及状态证据
- 来源列表及各自角色：企业官网、ATS、授权招聘平台、校招转载、搜索摘要

### 候选资格

- 2027 届是否明确
- 本科/硕士要求、专业要求及“可以投”与“优先”的区别
- 经验要求、实习要求、毕业时间、语言和证书要求
- 是否存在学校名单、党员、户籍或人才项目等限制

### 薪资

- 保留完整原文，例如 `10–20K·16薪`、`面议`、`年薪 20 万`、`底薪+绩效`
- 明确固定/浮动、试用期、奖金、补贴、绩效和是否保证发放
- 若单位和周期明确，可标准化月薪上下限及广告年化月均中点；必须标注是“广告值”
- 年发月数未知时，不要自行假定 16 薪或把最高值年化；只能用 12 薪压力测试另列
- 月薪区间极宽、只显示上限、面议或提成占主导时，降低证据等级并保留区间

### 工作条件

逐项记录页面原文，并分别标记 `explicit_yes`、`explicit_no`、`unknown`：

- 标准工时、固定双休、周末值班、白夜班或轮班
- 出差频率、单次时长、海外/国内、临时到场
- 现场调试、工程实施、驻场、客户现场或洁净室
- 住宿、宿舍扣费、班车、餐补、交通补贴
- 工作地点是否是岗位实际驻地，而非仅公司注册地址
- 试用期、签约主体、社保公积金基数和缴纳地（能取得时）

用户接受现场调试或工程实施，不代表同时接受频繁出差或长期驻场。必须分栏判断。

## 证据与确认层级

沿用本技能的 A–D 证据等级，并额外记录“由谁确认”：

| 确认层级 | 典型证据 | 使用方式 |
|---|---|---|
| 书面 offer / HR 书面确认 | 邮件、盖章/电子 offer、聊天中的明确书面答复 | 可确认实际条款，但保留文件访问权限 |
| 企业当前原始招聘页 | 企业官网、ATS、官方招聘系统 | 可确认广告条款和当前页面状态 |
| 授权平台原始职位页 | 平台职位 ID 与完整详情 | 可核验广告字段，需防止平台缓存和转载 |
| 第三方转载/搜索摘要 | 校招转载、聚合站、引擎摘要 | 只能辅助发现，不能单独支撑结论 |
| 口头/个人转述/截图 | HR 电话、员工口述、社交媒体 | 标为待书面确认，不作硬条件通过 |

页面显示的具体薪资、双休和出差标签即使来自企业官方页，也仍可能在实际劳动合同中变化；只有书面 offer 或 HR 书面确认才能把“广告条件”升级为“实际条款”。

## 与用户条件匹配

单独输出三个结果：

```text
明确满足
明确不满足
未确认
```

只有原始页或书面材料明确支持时才能写“明确满足”。“未确认”不得折算成“不要求”，也不得为了扩大机会池把它写成通过。最终给出：

- 当前是否值得投递
- 哪些是硬门槛
- 哪些条件必须在初筛或面试前书面确认
- 若薪资或班制不满足，是否有仍值得保留的岗位价值

## 单岗位核验卡

默认先在对话中交付以下结构；用户要求文件时再生成 Word/Excel/HTML：

1. 结论：找到/未找到原始岗位，是否开放，是否匹配目标届别专业。
2. 岗位身份：企业、岗位名、岗位 ID、地点、来源、最后核验时间、匹配置信度。
3. 薪资：原文、范围、年发月数、广告年化月均中点；若缺失则列为未取得。
4. 条件矩阵：双休/轮班、出差、驻场/现场实施、住宿/班车、社保公积金、签约主体。
5. 证据：主来源、交叉来源、证据等级和页面日期。
6. 空缺与风险：已关闭、疑似过期、地点不一致、专业可投性不明、平台转载等。
7. 下一步核验：给 HR 的逐项书面问题。

若需要并入城市报告，只把该岗位作为一条岗位记录，并保留以下附加字段：`requisition_id`、`canonical_url`、`job_status`、`status_verified_at`、`match_confidence`、`source_role`、`condition_confirmation_level`。没有这些字段时可在 `notes` 中写明，不改变现有 `jobs.csv` 的必填字段。

## 停止条件与限制

出现以下任一情况即可交付阶段性核验，而不是无限扩展：已确认原始岗位身份和当前状态；原始页、授权平台和公开搜索均无法定位；遇到验证码、登录失效或平台限流；继续查询不会改变候选或结论。

报告必须写明未覆盖的平台、页面不可用时间、无法确认的专业资格、薪资口径和岗位状态。不得保存 Cookie、账号密码、验证码或未经处理的个人聊天截图。
